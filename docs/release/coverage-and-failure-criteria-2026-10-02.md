# 失败解释与覆盖率口径封口 — 2026-10-02

> 性质：发行口径封口（**不新增扫描、不改扫描器逻辑、不清洗历史记录**）
> 对象：Resume 修复后自然完成的验证项目（验证副本 DB，本轮以 `sqlite3 -readonly` 只读复核）

> 核心边界：**「扫描完成」不等于「每个文件内容都完成哈希校验」**

## 1. 为什么必须封口

NDG 的分层哈希设计决定：**完整内容 SHA-256 只对重复候选计算**，而非对每个文件逐字节校验。历史任务另存在 3 条哈希失败，且旧版本未持久化逐项失败原因。

若发行口径不区分维度，用户会把「扫描完成」误读为「全部内容已逐字节校验」，从而高估清理决策的安全性。因此本口径的作用是**把能力边界写成可核验的三条陈述**，而不是继续修改扫描器把失败计数清零。

**结论**：**不能宣称"全部内容均完成校验"**。对外只能按上述三项分别陈述；3 条历史哈希失败的单项原因**不可追溯**（旧版本未写入逐项记录），作为**已知限制**保留，不做推测、不做回填。

## 3. Public Beta 表述要求（强制）

下一候选（预计 `v0.5.0-beta.5`）的发行说明与产品界面必须表达：

1. **遍历已完成**：扫描任务自然完成，checkpoint 为 `completed`；
2. **文件存在状态**：`active / unavailable / missing` 三态分别说明；`unavailable` 表示扫描时不可读取，**不等于**数据丢失；
3. **内容校验覆盖**：快速哈希覆盖全部条目；完整内容校验按分层设计仅作用于重复候选；**不得**出现"100% 内容已校验""全部内容均已验证"类表述；
4. **已知限制**：3 条历史哈希失败原因不可追溯；26 条 `unavailable` 的原始时刻错误不可回溯（代表探针为当前 `ENOENT`）。

上述四项为发行说明的**必含条款**；写不清这四项，不满足 Public Beta 的表述门槛。
