# Purge 旧日志恢复：保留未决状态（2026-10-16）

这是负向安全收口，不是永久删除或自动恢复能力验收。所有公开入口继续使用 `PurgeReleaseAllowed() == false`；没有新增开关、维修参数或人工强行结案入口。既有公开发行物不变，本次只使用新建临时数据库和人工文件。

## 问题与结果

旧 `rollbackStaged` 忽略 rename 和数据库错误，却把内存计划标为 `ROLLED_BACK`。旧恢复流程还会凭 `commit_pending` 且两个路径不存在推定 unlink 已完成，或凭路径存在推定可以移动／结案。旧日志只有路径、大小和摘要，没有绑定挂载／根目录、受控暂存对象或已完成 unlink 的持久证据。相同内容、名称缺失或名称重现都不能补足这一证明。

现在 `BeginPurge` 成功后的任何失败保留 active journal，不执行自动回移，也不标记已回滚。取消在建暂存目录、首次移动及不可逆删除前重新检查；已经发生的动作仍保留未决。旧日志的 `pending/staged/commit_pending` 一律返回固定 `manual_reconciliation_required`、`StepFailed`、非 nil 安全错误和空终态，不检查路径来推定成功，不修改隔离内容或 Purge 业务表。读取失败返回安全通用错误，不透出数据库原始细节。CLI 汇总改为“inspected / unresolved”，避免称已完成恢复。

未决日志持续触发项目 Recovery Lock，关闭并重开数据库也不会解除。历史终态不重写，也不由本次补认证。未来只能通过另行独立审查、具有充分身份及持久证据的恢复协议处理这些记录，不能直接把日志字段改成已完成。

## 验证范围

- 三种 active journal 状态 × 八种真实临时文件形态：仅原文件、仅暂存、两者同内容、两者缺失、两者不同内容、暂存符号链接、暂存目录、根目录被替换。每组关闭／重开真实 SQLite 两次，检查 journal、plan、item 全字段一致、文件证据不变及 Recovery Lock 仍生效。
- 七类注入故障覆盖暂存目录、首次移动、staged 写入、暂存摘要、commit_pending 写入、unlink、最终提交；另加删除前和暂存前取消。检查实际保留的字节、active journal 和非终态。unlink 成功而持久提交失败的人工场景保留 `commit_pending`，不得伪称回滚。
- 日志读取失败检查通用错误、不泄漏 canary、不返回成功；原有禁用策略及安全拒绝回归继续运行。

这里的“不修改”仅指恢复 executor 的隔离内容和 Purge 业务状态。外层 CLI 会打开／迁移数据库、创建执行锁并写私有回执，不能声称整条命令零写入。这些是本机开发测试；不认证真实 NAS、挂载竞争、断电、签名 Mac 发行物或公开资产。

## 继续阻断的能力

正向执行中的路径竞争、同设备嵌套挂载、根目录替换、暂存命名与目录权限、descriptor 绑定、目录 fsync 和不可逆提交证明仍需完整方案及真实正反测试。现有 `st_dev` 比较不足以认证挂载边界。不得因为本次拒绝测试通过而开启 Purge。fnOS 客户端入口、Darwin 正向核验及新的治理发行候选各自保持未完成状态。
