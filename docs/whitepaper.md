# 面向 NAS 的本地化数据治理与安全归档白皮书

版本：1.0（2026-07）

许可：CC BY 4.0，详见 [`LICENSE-DOCS.md`](../LICENSE-DOCS.md)

## 摘要

大容量 NAS 的问题往往不是“文件太多”，而是文件的内容、路径、用途、版本、备份关系与归档责任混在了一起。传统重复文件工具通常只回答“两个文件是否相同”，却无法回答“其中一份是否多余”“应保留哪一份”“清理是否会破坏业务或证据链”。

本文提出一套本地优先、只读优先、证据驱动的数据治理方法：先建立文件事实，再识别内容关系和目录语境，随后生成可解释的处理计划，最后由独立执行层在 stale 检查、隔离、校验、审计和回滚保护下实施。核心判断是：

> 内容相同是技术事实；是否冗余是语境判断；是否执行是风险决策。

本文仅包含抽象模型、通用流程和合成示例，不包含真实人物、客户、设备、路径、文件名、容量、目录树或扫描数据。

## 1. 问题定义

同一份二进制内容可能同时位于正式归档、项目工作区、证据目录和备份介质中。即使完整 SHA-256 一致，这些文件仍可能承担不同职责。反过来，同一逻辑资产也可能由不同编码或不同阶段的多个文件共同构成，例如源文件、编辑工程、预览、导出和交付版本。

因此，治理系统至少需要分别回答：

1. 内容是否完全相同、等价、相似或存在派生关系？
2. 路径所在目录承担什么职责？
3. 两份存储是否属于同一用途、不同用途或备份关系？
4. 是否存在唯一文件、依赖、原始记录或证据链风险？
5. 哪个对象适合作为保留项，依据是什么？
6. 操作是否可以被验证、撤销并完整审计？

系统目标不是最大化释放空间，而是在不破坏数据含义和来源链的前提下，降低无价值冗余并建立可持续维护的数据秩序。

## 2. 基本原则

- 默认只读。扫描、分析和计划阶段不改变被治理数据。
- 内容相同不等于可删除；目录职责与存储用途必须共同参与判断。
- 保护规则优先于清理规则；冲突进入人工复核。
- 不跟随符号链接，不跨挂载点，不越过显式任务根目录。
- 分离扫描、分析、计划、审批、执行、校验与审计。
- 破坏性操作必须具备 stale 检查、隔离、校验、审计和回滚能力。
- 外部 AI 默认关闭；敏感路径、文件名和内容不进入普通日志。
- 相似关系、版本关系和派生关系只用于解释，不自动授予删除权限。

## 3. 统一对象模型

### 3.1 文件实例

文件实例表示某个存储位置上的实际文件。它包含存储标识、相对路径、大小、文件系统时间、权限、文件标识、链接状态、首次发现时间和最后验证时间。路径不同即表示不同实例，即使内容完全相同。

### 3.2 内容对象

内容对象表示二进制内容本身。多个文件实例在完整哈希一致时可以指向同一个内容对象。内容对象记录大小、快速指纹、完整哈希、真实格式、可解析状态和完整性结论。

### 3.3 表现形式

表现形式表示同一逻辑内容的不同编码或封装，例如源图与导出图、无损音频与压缩音频、编辑文档与固定版式导出。它们不是字节级重复，却可能属于同一资产。

### 3.4 逻辑资产与资产组

逻辑资产是用户认知中的一个数字对象；资产组是围绕同一事件、项目或事项形成的文件集合。一个资产组可能同时包含源文件、工程文件、依赖、预览和交付物，不能按普通重复文件组处理。

### 3.5 目录语境

目录语境将路径转化为结构化职责，例如：

```json
{
  "scope": "organization",
  "domain": "project",
  "directory_role": "formal_archive",
  "archive_state": "completed",
  "privacy_level": "restricted",
  "authority_level": 90
}
```

示例字段均为合成值。真实系统应避免把敏感路径直接写入普通日志或公开报告。

## 4. 文件关系分类

系统应至少区分以下关系：

- 字节级完全重复：大小相同且完整哈希相同。
- 解码内容等价：封装或元数据不同，主体内容等价。
- 视觉、听觉或文本近似：仅表示相似，不能自动删除。
- 版本关系：草稿、修订、签署、发布或分支版本。
- 原始与派生：源文件与转码、导出、缩略图、转写等结果。
- 工作副本：为编辑、传输或临时协作生成的副本。
- 镜像与备份：主存储、本地备份、异地备份、快照或冷备份。
- 交叉归档：相同内容为不同业务职责分别保存。

只有“内容重复”和“存储职责重复”同时成立，才可能构成可清理冗余。

## 5. 目录角色与保护边界

常见目录角色包括原始资料、正式归档、项目工作区、临时区、未整理区、备份域、缓存与派生区、敏感区以及系统与应用目录。

目录角色不能只靠名称猜测。系统应结合上级目录链、分叉点、时间范围、内容构成、用户定义的保护范围与存储拓扑形成证据。以下规则具有优先级：

1. 系统保护规则；
2. 用户明确保护规则；
3. 目录角色与存储职责规则；
4. 文件类型和依赖规则；
5. 去重与整理规则；
6. 垃圾和缓存候选规则；
7. 默认保守规则。

备份域、系统目录、数据库、虚拟机镜像、工程依赖和敏感目录默认不进入通用自动清理。

## 6. 渐进式分析

为控制机械硬盘和 SMB 网络上的 I/O，分析应按成本逐级提升：

- L0：只读文件系统元数据，如大小、时间、权限和链接状态。
- L1：通过扩展名、MIME、magic bytes 或容器头识别真实格式。
- L2：读取有限数据块形成快速指纹，只用于筛选候选。
- L3：仅对必要候选计算完整 SHA-256，证明字节级相同。
- L4：使用有界、只读的格式解析器提取可验证元数据。
- L5：可选的 OCR、感知指纹、语义或 AI 分析；敏感范围默认禁用。

完整哈希应缓存并在文件大小、修改时间和文件标识未变化时复用。网络存储应限制并发，避免多个大文件同时顺序读取造成带宽争抢。分析失败应保留文件实例，并将详细路径写入权限受控的私有清单，而不是普通日志。

## 7. 两阶段决策模型

第一阶段判断内容关系，输出完全相同、等价、相似、同源、版本、派生或未知。第二阶段判断存储关系，输出同职责冗余、工作副本、迁移残留、交叉归档、备份、不同用途或未知。

自动处理候选至少需要同时满足：

```text
完整哈希一致
AND 目录职责一致
AND 不属于备份域
AND 不属于保护范围
AND 不存在工程或应用依赖
AND 保留项明确
AND 文件状态在执行前未变化
```

任何条件不满足都应降级为人工复核。保留项评分只能在同一职责内部比较，不能跨职责决定删除。

## 8. 安全工作流

推荐流程为：

```text
扫描 → 分析 → 生成计划 → 人工审批 → 执行前复核 → 执行 → 校验 → 审计
```

每个阶段产生独立、可检查的输出。扫描器不写源数据；分析器只生成事实和关系；计划器只生成草案；审批只改变计划状态；执行器只接收已批准且仍然有效的计划。

操作计划应包含任务标识、源和目标、动作、理由、内容证据、目录语境、风险级别、保留项、规则版本和执行状态。真实路径应只存在于受控的私有计划和审计介质中。

## 9. 执行、隔离与回滚

默认处理方式应是隔离而非永久删除。隔离记录保存原始位置、隔离位置、权限、时间、哈希、理由和恢复信息。

执行前重新检查路径存在性、大小、修改时间、文件标识、哈希和目标状态。任一事实变化即将计划标记为 `STALE` 并停止该操作。

跨卷移动必须实现为“复制、校验目标、再处理源”。至少验证大小、完整哈希、权限、元数据与目标可读性。复制或校验失败时不得删除源文件。执行日志和恢复记录必须先于不可逆步骤持久化，并覆盖中断、重启和回滚测试。

### 9.1 分级删除与最终永久清除

删除生命周期分为四级：L0 仅建议、L1 可恢复隔离、L2 带保留期的延时删除、L3 永久清除。L1/L2 仍属于可恢复操作；保留期届满只允许生成新的 `DRAFT` 清除计划，不得自动升级为 L3。

L3 必须由独立执行器完成，并同时满足：对象已存在于受管隔离台账；不处于保护 HOLD；保留期已届满；单项计划经过二次人工审批；审批摘要在执行时再次匹配；隔离路径、大小和完整哈希未变化；路径未越过隔离根目录、未经过符号链接、未进入嵌套挂载点。

永久清除的提交点是经同卷 staging 和第二次完整哈希校验后的文件移除。提交前失败必须恢复到隔离路径；提交后发生日志落盘中断时，通过持久化的 `commit_pending` 状态与 staging 是否存在进行对账。永久清除不提供批量 `--all`，不允许直接作用于源目录。

这里的“永久”表示从当前文件系统命名空间不可恢复地移除，不代表覆盖 NAS 快照、备份、RAID、写时复制文件系统或 SSD 介质残留；后者属于存储基础设施的数据销毁流程。

## 10. 隐私、日志与 AI

治理系统可能接触身份、财务、医疗、法律、家庭影像与商业资料，因此应采用本地数据库、本地处理和最小日志。普通日志只输出聚合数量、阶段、耗时和错误类别，不输出真实路径、文件名或内容片段。

AI 适合解释目录语义、生成分类建议、总结复核结果和起草规则；不应独立决定永久删除、覆盖、跨备份域去重或处理证据性资料。AI 输出必须标记依据、置信度、风险与人工确认要求，外部 AI 默认关闭。

## 11. 可审计架构

推荐模块包括只读扫描器、索引、格式识别、哈希服务、目录语境引擎、关系引擎、规则引擎、计划器、审批接口、独立执行器、隔离管理、校验器和审计存储。

关键数据可分为：存储与文件实例、内容对象、元数据、目录语境、分类、重复组、资产关系、操作计划、执行日志、规则、保护路径和扫描错误。分析数据库不应成为执行授权本身；批准状态、执行配置和源根目录约束必须被独立验证。

## 12. 测试与发布门槛

测试数据应完全合成，并覆盖同目录副本、跨目录副本、交叉归档、备份关系、版本、派生、损坏文件、零字节、链接、跨卷、权限不足、处理中变化、同名不同内容和不同名相同内容。

安全测试至少证明：

- 唯一文件不会被清理；
- 不越过任务根目录或挂载边界；
- 符号链接不会绕过路径约束；
- 复制失败或校验失败不处理源文件；
- 文件变化会使旧计划失效；
- 中断后可恢复，隔离后可回滚；
- 审计信息完整且普通日志已脱敏。

## 13. 实施路线

1. 安全索引：只读扫描、格式识别、分层哈希、索引和重复报告。
2. 语境与计划：目录角色、保护范围、关系分级、保留证据和草案计划。
3. 安全执行：审批、隔离、stale 检查、跨卷校验、审计和回滚。
4. 格式扩展：使用有界只读解析器支持常见媒体、文档和压缩格式。
5. 资产治理：版本、派生、资产组、目录合并建议和可选的本地智能分析。

每一阶段都应先冻结安全边界和验证门槛，再扩展识别能力或自动化范围。

## 结语

可靠的数据治理处理的是“文件实例、内容对象、目录语境、存储职责、资产关系、时间证据与风险边界”的组合，而不是孤立文件。衡量系统质量的指标也不应只是释放了多少空间，而应包括事实覆盖率、误判率、人工复核负担、操作可恢复性和长期目录可靠性。

这套方法的最终目标，是让个人、家庭和组织能够在本地、可解释、可验证的前提下维护长期数字资产，同时把破坏性动作始终留在明确审批和独立执行边界之后。
