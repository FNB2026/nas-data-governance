# ADR-0009：双入口永久删除（隔离区清理与源文件直接清理）

状态：产品范围已由用户批准；技术实现与平台发布仍须分别验收。

日期：2026-11-20

关联：ADR-0005、AGENTS.md、Issue #140、Phase 2 Governance Execution Closure。

## 背景

ADR-0005 建立了分级删除生命周期：源目录的普通 `DELETE` 实际进入隔离区，永久 PURGE 只作用于已登记、到期且未受保护的隔离项。用户现明确要求两种永久删除入口都成为 NDG 产品能力：

1. 清理已进入 NDG 受管隔离区的文件。
2. 从扫描/重复候选结果中，直接永久删除用户明确选择的源文件，不要求先进入长期隔离区。

本 ADR 扩展产品范围，但不抹去 ADR-0005 的历史决策。两条永久删除路径必须保持独立的领域模型、计划、授权、执行器、Journal 和能力声明。

## 决策

### 1. QUARANTINE_PURGE：隔离区永久清理

- 仅针对数据库登记的单个 `quarantine_items`，调用方只能提交 item ID，不得提交任意文件路径。
- 只允许隔离保留期已届满、状态符合清理条件且无 HOLD 的项目。
- ADR-0005 的默认 30 天保留期继续有效。
- 计划、审批、Dry Run、执行必须是分离步骤。
- 审批摘要绑定 plan ID、item ID、隔离路径、内容 SHA-256、大小、保留期、隔离根和对象/挂载身份。
- 执行前重新验证审批摘要、对象身份、完整内容哈希、根目录绑定和挂载边界。
- 持久化 Journal 必须先于文件系统变更。任何不确定状态必须保留证据并保持恢复锁，禁止猜测提交结果或自动解锁。
- 永久清理只能表示当前文件系统命名空间中的文件名/对象被移除；不承诺覆盖物理介质，也不保证删除快照、备份或底层存储副本。

### 2. SOURCE_DIRECT_PURGE：源文件直接永久清理

- 这是独立的新操作类型，不是普通 `OperationDelete` 的新含义。现有 `OperationDelete` 继续表示 `delete_to_quarantine`。
- 只能从当前项目、当前扫描代次中仍为 active 的文件实例创建计划。服务端必须从持久化扫描记录解析对象；客户端提供的路径字符串不能成为删除授权。
- 用户必须明确选择具体文件。UI 可以多选，但后端必须将选择拆成 N 个单文件计划、审批、Dry Run、执行和回执。各项独立成功或失败；不得提供目录删除、通配符、`--all`、自动执行或基于模型建议的隐式删除。
- 不要求先进入长期隔离区，也不适用 30 天长期保留期；但每个文件仍必须经过独立审批、成功 Dry Run、执行前再次核验和明确的二次确认。
- 只允许普通文件。符号链接、目录、设备文件、socket、FIFO、越出授权 storage root 的对象、跨越未授权挂载边界的对象必须拒绝。
- 保护规则优先：敏感、原始源、备份、系统目录、受保护格式、目录语境冲突及身份不确定项默认拒绝或进入人工复核。唯一副本可以由用户显式选择，但必须显示“当前扫描范围内未发现独立副本”的高风险警告，并要求额外的明确确认；系统不得自动将唯一副本列入批量删除。
- 若文件属于重复组，计划必须绑定重复组和保留副本证据；执行前确认不会因扫描过期或并发变化而误删用户指定的保留项。硬链接路径与物理对象必须区分，预估可回收空间不得把路径数当作物理副本数。
- 审批摘要至少绑定 project/storage ID、scan generation、file instance ID、根相对路径、device/inode、可得的 mount ID、link count、size、mtime/ctime、mode、SHA-256、重复组/保留证据和目录语境决策。
- 执行器必须采用平台原生 rooted/descriptor-relative 操作，不能以“按路径检查后再按路径 unlink”作为安全证明。允许使用同卷、私有、短时 transaction staging（不属于用户可恢复的长期隔离区）：执行前持久化意图，绑定根/父目录/文件描述符身份，原子进入 staging 后再次核对 staged object 与已打开对象一致，再持久化不可逆 commit intent 后执行 unlink。提交前失败只能恢复被证明属于本计划的对象；无法证明时保留证据并保持恢复锁。
- UI 必须显示目标文件、目录角色、删除原因、大小、哈希短标识、重复组与保留副本、物理副本数、预计可回收空间、唯一副本/不可恢复警告和逐项结果。用户应能在提交前取消单项。

### 3. 执行边界与平台策略

- Web 进程只负责身份验证、计划展示、审批和请求编排，不直接持有源文件写权限。独立、低权限 Worker 是 Linux/Docker 的实际执行主体。
- `QUARANTINE_PURGE` 与 `SOURCE_DIRECT_PURGE` 使用独立 capability / release gate。不得通过一个总开关意外同时开放两个入口。
- 生产能力默认拒绝。不得使用环境变量、UI 参数、客户端字段或临时 feature flag 绕过门禁。
- 第一交付目标为 Linux/Docker：先完成隔离区 PURGE，再完成源文件直接 PURGE。只有精确提交上的测试、独立复审和正式候选验收完成后，才逐项开放对应能力。
- macOS：Darwin P0 的安全根目录与挂载边界证明完成前，两条写入型 PURGE 均保持拒绝；Linux 证据不能替代 Darwin 证明。
- fnOS：复用经过验证的 Linux 实现，但真实 fnOS 现场验收前不得宣称正式支持；整机重启按用户维护窗口另行安排。
- Windows 不属于本 ADR 的首批交付范围。

### 4. 失败与恢复

- Journal 必须先于任何文件系统变更持久化。
- 对每个不可逆边界建立故障注入与 SIGKILL 测试，包括 intent、staging rename、目录 fsync、staged identity verification、commit intent、unlink 和数据库最终提交。
- 对象身份、挂载身份、Journal、数据库终态或目录清单任何一项不一致时，不得显示成功，不得释放恢复锁。
- 恢复只允许在有持久证据证明的状态下自动完成；否则进入人工对账并保留所有可见数据。
- 执行结果和审计不得在普通日志中泄露完整敏感路径、文件名或内容。

## 不在本决策范围内

- 物理介质安全擦除、SSD secure erase、磁盘快照销毁、备份生命周期管理。
- 自动识别并自动永久删除。
- 未经用户明确选择的批量/目录级永久删除。
- 通过旧 Beta、Docker Preview 或历史审批记录追溯开放 PURGE。

## 验收条件

1. 两条路径有独立计划/审批/执行/Journal/API/Worker capability。
2. 单项与多选逐项执行的成功、失败、取消和部分失败均可审计。
3. stale、symlink、目录、特殊文件、mount/bind mount、根/父目录替换、hardlink、路径 ABA、身份变更均有拒绝或安全处理测试。
4. 唯一副本、敏感/备份/原始/系统目录、目录语境冲突有明确保护与确认测试。
5. 审批摘要篡改、重放、重复字段、并发请求、重复点击和扫描代次过期均拒绝。
6. 每个持久化/文件系统提交边界均有故障注入与恢复测试。
7. 使用合成文件和独立临时项目验收；不得使用生产 NAS 原始数据作为破坏性测试夹具。
8. UI、API、CLI、Worker、能力声明和发行门禁一致。
9. 每个平台仅在自己的精确提交和真实环境证据通过后开放。旧版本发行资产保持不变。

## 与 ADR-0005 的关系

ADR-0005 对原有隔离区生命周期和普通 `OperationDelete` 的约束继续有效。ADR-0009 新增 `SOURCE_DIRECT_PURGE` 独立通道，并要求重新设计安全执行协议；它不授权把旧 `PurgeExecutor` 的路径操作直接解锁，也不改变旧 `OperationDelete` 的语义。
